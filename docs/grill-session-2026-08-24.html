01 / 新增设计

thread 生命周期五阶段契约

先说 thread 是什么:LangGraph 里每段会话都有一个存档编号(thread_id),checkpointer 以它为键,存这段对话的全部状态——消息历史、用户身份、悬而未决的写确认。「多轮对话记得住」和「写操作挂起、人工确认后恢复」两个能力都落在它身上。缺漏扫描把它判为全架构最大空白(P0,「上线即撞」):五个阶段(诞生/属主/并发/终结/跨入口)各自缺规则。本节把 thread 从「隐式存在」升级为显式契约;原则由 Zewang 提出:每个用户只能控制/访问自己的信息,权限校验在恢复路径,不在仅创建路径。

图 7 · thread 生命周期五阶段 + 三个 P0 现场 + 暂缓项 + 属主原则

thread 生命周期五阶段契约

🔄 待同步新增
结论thread 是显式一等公民。①诞生:thread_id 命名规则 = 入口:用户:随机段(防猜防跨入口互踩);②属主:恢复/读取必须校验 thread 属主,否则可枚举翻别人会话(PII);③并发:同 thread 消息串行化(锁/队列),防 checkpointer 冲突与确认令牌错配;④终结:TTL 与 SEC-06 留存对齐,挂起确认载荷按 PII 处理;⑤跨入口:同一用户换入口接旧 thread 还是新开——v1 建议新开。原则:每个用户只能控制/访问自己的信息,权限校验在恢复路径,不在仅创建路径。
背景

会话管理缺口 的四个独立命中把它顶成 P0:同 thread 并发消息无串行化(,飞书连发两条→checkpointer 冲突/确认令牌错配);SSE「确认/拒绝」上行端点不存在(,ADR-0005 令牌机制在官网/CLI 侧无载体,拒绝后续流协议未定义);thread_id 命名规则/属主校验缺失(,CLI --session dev 与官网 SSE 同 thread 互踩,可枚举=PII 泄露);C 的 thread 切分未定(,三态机/卡片/速记隔离全悬空)。

暂缓项:SSE 断线重连/心跳/nginx 长连接调优由项目所有者 2026-08-24 暂缓,M5 前再定;「确认上行端点」不暂缓,仍属 M5 必做。

分析与理由

确认令牌机制(ADR-0005)依赖 interrupt 恢复路径,而恢复路径以 thread 为载体——thread 不显式,令牌就没有安全落点。命名规则解决「互踩」与「可枚举」两个独立问题:随机段防猜,入口+用户前缀防跨入口语义混乱。属主校验放恢复路径而不是创建路径,是因为创建路径无法防御「知道了别人 thread_id 就来恢复」的枚举攻击,只有每次恢复/读取都校验才能关闭。

利弊
利
  • 确认令牌在官网/CLI 侧有载体(SSE 上行端点)
  • 可枚举翻会话的 PII 泄露面关闭
  • 并发错配(令牌张冠李戴)消除
  • TTL 与留存对齐,挂起载荷不再无限驻留
弊
  • 新增锁/队列基础设施与清理 job
  • SSE 上行端点 = M5 必做的新增后端面
  • v1 跨入口新开会牺牲会话连续性(用户换入口即失忆)

03 / 新增设计

PII 分层边界:四道闸

隐私边界缺口 是 P0·红线级:原设计只在「进模型前」有一个脱敏节点,而 trace 在脱敏前就记录了原始 PII。grill 把脱敏从「节点」升级为「边界」,贯穿工具返回层 / 输出层 / trace 层 / 持久层四道闸。

图 5 · PII 四道闸:工具返回层(脱敏入口)· 输出层(复述守卫)· trace 层(采集点二次脱敏)· 持久层(留存对齐)

PII 分层边界四道闸

🔄 待同步新增
结论脱敏从「进模型前的单一节点」升级为「贯穿全链路的边界」:闸 1 工具返回层(脱敏下沉或采集点二次脱敏,路线待拍板)、闸 2 输出层(模型输出禁复述 PII)、闸 3 trace 层(Langfuse 采集点二次脱敏 + payload 禁入清单)、闸 4 持久层(checkpointer 挂起载荷 TTL 对齐 SEC-06;未声明摘要库补声明)。
背景

隐私边界缺口 P0·红线级,六个独立命中: trace 记录脱敏前原始 PII(get_resume_detail 返回完整简历,脱敏节点在其后,叠加 OBS-01 全图上报 + ADR-0006「trace 全量」→ 原始 PII 直落 Langfuse); 输出侧无守卫(模型生成的面试题/报告可能复述简历里的手机号/QQ); 占位符映射契约缺失(存哪/是否确定性/还原白名单——影子运行对不上、面试题可能泄漏占位符); checkpointer 挂起载荷(含姓名/时间/原因)TTL 与 SEC-06 留存无对齐; 速记比简历更敏感(面试官主观评价),留存策略未含; 跨年查重(EVA-10)依赖被脱敏抹掉的身份键,且「往年摘要库」是未声明的 PII 仓库。

分析与理由单一脱敏节点的假设是「PII 只出现在模型输入这一条路上」,但审计与观测需求(ADR-0006 trace 全量)天然把数据复制到 Langfuse,持久化需求(interrupt 挂起载荷)把数据复制到 checkpointer——每条复制路径都是新的泄露面。四道闸的本质是「谁接触 PII,谁负责脱敏」:工具返回层是唯一知道 PII 长什么样的地方(确定性),输出层守卫防模型复述(规则+抽查),trace 层用禁入清单+二次脱敏兜底,持久层用 TTL 与留存策略限时存在。占位符契约必须确定性(可还原、白名单),否则影子运行对不上。
利弊
利
  • 单一节点失效即全链路泄露的风险关闭
  • 审计 trace 与 PII 合规可共存
  • 挂起确认载荷有明确生命周期
弊
  • 四道闸分散实现,成本高
  • 需先拍板「权威脱敏层」,否则重复/矛盾

12.1 四段上下文组装 + 双 cache 断点

四段上下文组装 + 双断点

🔄 待同步优化
结论

组装顺序按「缓存稳定 → 易变」排四段,两个断点:

[全局静态前缀: 唯一 system prompt + 工具定义]   ← 所有用户逐字节相同,跨会话共享缓存
─── cache 断点 1 ───
[会话稳定块: 身份/角色/当前周期]                ← 会话内不变,第 2 轮起命中
[轨迹: 对话消息,append-only]                    ← 只增不改
[易变块: 代码维护的状态栏,user 角色消息挂末尾]   ← 每轮尾部替换,失效范围仅自身
─── cache 断点 2(可选) ───

三条铁律:①system prompt 全局唯一变体——角色/身份一律进断点后的稳定块,绝不烘进 system prompt(断点前每多一个运行时条件,缓存键变体翻倍 2^N);②易变块选「尾部替换」而非「持久追加」(Claude Code <system-reminder> 是持久追加的对照:状态栏位于轨迹末尾,删旧加新的失效范围只有自己;会话 <40 轮时持久追加只会积累陈旧状态,留作长会话备选);③状态栏必须代码维护(从图状态确定性派生),绝不交给模型批量统计。

裁剪与压缩阈值前不动(招新对话大多 <40 轮);超阈值后批量上下文感知摘要,禁止滑动窗口与按长度硬切;摘要提示词携带当前查询意图与上下文;固定保留清单:[决策、约束、失败路径、引用];摘要用 strong 模型(「压缩即理解」,压缩模块能力需接近主模型);压缩熔断器——连续 N 次压缩失败即停,降级并上报人工;实现惰性——契约现在冻结,实现等真实长会话出现(触发指标:单会话 >40 轮成为常态)。
背景仓库此前没有上下文组装约定。两个天然张力:对话消息 append-only 对 prompt cache 最友好,而状态类内容每轮变化;裁剪省 token 但破坏缓存前缀。校准依据三条结论:缓存前缀须逐字节稳定;压缩须任务感知且批量进行;滑动窗口式丢弃会同时破坏缓存与关键工具结果。

12.5 Checkpointer 存储:Redis vs Postgres(ADR-0007)

Redis vs Postgres(倾向 PG)

🔄 待同步待讨论
结论倾向 Postgres,三条理由按分量排:①延迟优势在本负载归零——checkpoint 写入发生在每个 super-step 末,每步内含 LLM 调用(0.5~5s),Redis ~0.5ms vs PG ~3ms 的差 <1% 步耗时,用户不可感知;②持久性是分水岭——Redis 默认内存态重启全丢,AOF everysec 仍有 ≤1s 丢失窗口,内存压力下 noeviction=写报错、allkeys-lru=逐出挂起 interrupt(确认静默丢失),丢挂起确认是生产事故级风险,与 fail-closed 哲学相悖;PG WAL+fsync 提交即持久;③运维账——PG 已在部署图(Langfuse 自带 PG;M4 pgvector),checkpointer 用 PG 则 Redis 可从 agent 栈整体退场(v1 限流/预算=进程内),有状态服务 2→1,备份=标准 pg_dump/PITR,thread 状态可 SQL 运维查询(找挂起确认/僵尸 thread)。
Redis 的真实论点与回应①原生 TTL:真实优势,但 PG 侧一条清理 job(DELETE ... WHERE updated_at < ... 挂 cron)可替代,换来不被逐出的确定性;②「聊天热数据放热存储」直觉:在 LLM 步耗面前不成立(理由 1)。
若最终选 Redis 的底线三件套AOF 开启 + maxmemory-policy=noeviction + 内存容量规划(会话数×平均 checkpoint 大小)。三者缺一即挂起确认有静默丢失路径,须回写 ADR-0005 风险清单。

15.3 thread 五点 + 原则(已记录,双方共建)

  1. 诞生:thread_id 命名规则 = 入口:用户:随机段(防猜防跨入口互踩)。
  2. 属主:恢复/读取必须校验 thread 属主——否则可枚举翻别人会话(PII)。
  3. 并发:同 thread 消息串行化(锁/队列),防 checkpointer 冲突与确认令牌错配。
  4. 终结:TTL 与 SEC-06 留存对齐;挂起确认载荷按 PII 处理。
  5. 跨入口:同一用户换入口接旧 thread 还是新开(v1 建议:新开)。
原则(Zewang) 每个用户只能控制 / 访问自己的信息;权限校验在恢复路径,不在仅创建路径——创建时校验挡不住「知道 thread_id 就来恢复」的枚举攻击,恢复/读取路径才是 PII 防线的最后一道。
