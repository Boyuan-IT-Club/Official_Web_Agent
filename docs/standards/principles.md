# 设计原则（SOLID / DRY / KISS）

> **何时读**：设计新模块/抽象、评审分层与接口、纠结「要不要再抽一层/一个接口」时（写代码行进中的随手判据）。
> **一句话**：原则是判断工具不是目标——**先用 KISS 交付当前需求的最简解，用内聚/耦合判断往哪长，用 SOLID 定形状，用 DRY 定知识住哪**；原则打架时按这个次序裁决。

## 裁决次序（原则冲突时的裁判）

1. **KISS 先行**：满足当前需求的最简方案优先。禁提前设计与提前优化（为想象中的需求预建抽象/扩展点）；禁重复造轮子——动手前先找轮子：项目内既有实现 → 成熟第三方库。
2. **DRY 管知识**：同一知识（规则/常量/流程/契约）只允许**一个权威出处**。两处重复且**会一起变** → 合并；只字面相似但演化方向不同的「假重复」不合并——强行共享是制造耦合（两处将来独立改，焊死的抽象两头受害）。
3. **SOLID 管形状**：变化信号出现时才动用——SRP 拆职责、DIP 倒置依赖、ISP 拆接口。抽象时机判据：**第二次因同类原因改同一处时**才抽（rule of three 的严格版），第一次容忍重复。

## SOLID 应用要点（每条落到本库的具体文档）

| 原则 | 操作化判据 | 落点 |
|---|---|---|
| **SRP** 单一职责 | 一个模块只有一个「变化的原因」；一句话说清职责、说清时不用「和/同时」 | 函数（readability）、层（layering）、测试一测一行为 |
| **OCP** 开闭 | 新需求 = 加代码而非翻改旧代码；但**扩展点只在第二次同类变化时建**，YAGNI 优先于 OCP | layering 加层信号 |
| **LSP** 里氏替换 | 接口的任何实现（真实现/内存 fake/子类）可无感互换：不收窄输入、不加意外异常、行为契约一致 | 端口接口与其测试替身 |
| **ISP** 接口隔离 | consumer 只依赖自己用到的方法；胖接口按消费方拆小 | 「端口在 consumer 侧声明」（layering） |
| **DIP** 依赖倒置 | 上层声明自己需要的抽象，下层实现它；依赖指向稳定的一方 | layering 依赖规则全文 |

## 高内聚低耦合（前两条的原则化表述）

- **内聚**：相关的变化住在一起。判定问句：改这个需求，diff 集中在一个模块/包里吗？分散 = 内聚出问题（按 feature 分包、领域函数归位是解法）。
- **耦合**：这个模块变了，会**被迫**改不相干的模块吗？会 = 耦合出问题（解法：依赖单向、跨层传简单结构、接口而非实现）。
- 内聚与耦合一体两面：分层、feature 分包、端口适配器，全都是「把相关变化圈在一起、把不相关变化隔开」的手段；**抽象是否值得，用「变化被圈住了没有」验收**，不用「看起来专业」验收。

## 反面清单

- 为复用而过早抽象：抽象错了方向，改起来比重复更贵。
- 教条 DRY 把偶然重复焊死成耦合（见裁决次序 2）。
- 「加个 Strategy/Factory 显得专业」：无变化信号的模式是装饰品，KISS 直接否决。
- 原则背诵替代判断：每条原则都在问「这里未来会怎么变」，答不出来的地方不适用该原则。
