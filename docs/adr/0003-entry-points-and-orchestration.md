# ADR-0003: 入口形态与编排骨架——A 单循环,B/C 场景直连

- **Status**: Accepted
- **Date**: 2026-08-24

## Context

Agent 仓库现有骨架把三个能力模块(A 招新对话助理 / B 简历评估流水线 / C 面试官 Copilot)
全部画在聊天 Router 主图之下(GRA-01 身份解析 → GRA-02 意图分类 → GRA-03..06 硬分发)。
但三个模块的入口语义不同:B 是定时批处理,没有对话;C 的宿主界面(管理后台面试页)
本身就知道自己是谁;只有 A 的输入是开放式自然语言,意图未知。

编排选型阶梯(参照《深入理解 AI Agent》ch1:单次调用 → 工作流 → 自主 Agent):
B 恰好是可确定性分解的工作流,A 恰好是需动态决策的自主循环。
- **B**:调度器(job runner / cron)直连 evaluation 图,不经任何聊天路由。
  批量写回走评审确认语义(见 CONTEXT.md 词条),与对话确认是两套机制。
  **触发仲裁(2026-08-24)**:EVA-07「管理员在对话中触发」与「不经聊天路由」的冲突,
  以**遥控器模式**落地——聊天中提供 `trigger_evaluation(cycle_id)`(入队即回执)与
  `get_evaluation_progress()`(查进度)两个工具;对话是遥控器,不是流水线本身。

- **A**:Router 主图降级为「A 的前门」——身份解析(确定性代码:飞书 open_id /
  官网 JWT / CLI 模拟身份 → 用户+角色)→ 按角色装配工具集(确定性代码,SEC-02)→
  单 ReAct 循环(模型自主选工具,sonnet)。「意图」由工具选择隐式表达。
- **C**:宿主界面直连 copilot 图(INF-10 面板),界面即路由。
- **GRA-02 意图分类节点 v1 砍掉**。若未来 badcase 证明需要,只作软路由提示
  (决定初始提示词与工具预裁剪),不做硬闸。
- **工具绑定**:agent 进程内直接绑定 Python 函数;MCP server 纯对外暴露面
  (Claude Code 等外部消费者挂载用),不走协议回环。TOOL-07「经
  langchain-mcp-adapters 消费同一套工具」的描述作废。
- **工具描述契约**:docstring 写「何时用」而非「能做什么」,必须列边界条件
  (做不到什么、不接受什么输入),关键工具附 1~3 个真实调用示例。

## Consequences

- `graphs/router.py` 的 classify_intent 节点移除;GRA-02 issue 关闭或重标记为可选优化。
- GRA-03/04(问答/查询子图)合并为一个 assistant 循环;GRA-05(写子图)退化为
  interrupt 中间件 + 确认子流程,不是独立图。
- 遗留场景:若未来一个飞书 bot 同时服务候选人与面试官,webhook 层需按群绑定/身份
  分发——v1 不做,届时另立决策。
- **入口通道范围悬置**:C 已由项目所有者确认放官网管理端前端;A 是否接飞书
  (INF-05..07)还是仅官网 SSE + CLI,待与原设计者讨论(2026-08-24 提出)——
  结论可能收缩 INF 模块范围,届时更新本 ADR。
- 单循环的写操作安全不依赖意图分类,由三层承担:工具装配(读不到)+ interrupt
  确认(执行不了)+ 令牌校验(绕不过,见 ADR-0005)。
